# ShowGather V1.3 — Usability and Interface Plan

## Purpose

V1.3 makes the proven V1.2 product operable by a new operator and credible to
an audience without changing the presentation timing architecture.

```text
Canonical presentation command
  -> ordered outbox
  -> timed ID3/HLS or rehearsal SSE
  -> Player media-PTS scheduler
  -> presentation renderer
```

The Admin and Viewer use the same saved production data and presentation model,
but they serve different people and must be designed separately.

## Boundaries

V1.3 includes:

- Admin information architecture and guided workflows;
- preparation, rehearsal and live-operation workspaces;
- viewer desktop, mobile and TV layouts;
- a small shared visual foundation (tokens and accessible primitives);
- status, empty, validation and recovery states;
- preview surfaces that use the existing Player and presentation model.

V1.3 does not include:

- a new transport, renderer, event model or persistence model;
- authentication, permissions, collaboration, assets or template marketplace;
- drag-and-drop editing, plugins, billing, analytics or deployment expansion.

## Users and goals

| User | Primary goal | Interface quality required |
| --- | --- | --- |
| New operator | Create and save a first show without source-code knowledge. | Guided, explicit empty states and validation. |
| Show operator | Rehearse and run a programme safely under time pressure. | Fast, focused controls and unmistakable status. |
| Audience member | Watch a polished programme with useful companion content. | Clear hierarchy, responsive layout and accessible interaction. |

## Admin journeys

### 1. Onboarding and Prepare

```text
Open Admin
  -> choose or create production
  -> choose or copy a show configuration
  -> create or open rundown
  -> add typed cues
  -> preview the selected cue
  -> save
```

New installations must offer a clear first-production action. Seeded example
data remains optional inspiration, never a prerequisite for understanding the
workflow.

Low-fidelity layout:

```text
+----------------------------------------------------------------+
| ShowGather | Production selector                  API: healthy |
+--------------+-------------------------------------------------+
| Production   | Production details / show configuration         |
| Rundown      |                                                 |
| Graphics     | Cue list | Selected cue editor | Preview         |
| Settings     |                                                 |
+--------------+-------------------------------------------------+
```

The cue editor continues to use typed score, lower-third, alert, sponsor,
ticker and clear fields. Transport envelopes, database revisions and event IDs
stay diagnostic-only.

### 2. Rehearse

```text
Open saved production
  -> enter Rehearse workspace
  -> start/reset rehearsal session
  -> select desktop, mobile or TV preview
  -> trigger cues
  -> confirm output
  -> return to Prepare or proceed to Run
```

Rehearsal gets an unmistakable amber treatment and must state that it never
changes live presentation state. It keeps the existing rehearsal SSE channel
and immutable-session behaviour.

```text
+----------------------------------------------------------------+
| REHEARSAL ●  Production name                  API: healthy     |
+------------------------------+---------------------------------+
| Preview profile: Desktop      | Current cue / next cue          |
| [Programme preview]           | Cue result and validation        |
|                              | Reset rehearsal                  |
+------------------------------+---------------------------------+
```

### 3. Run

```text
Open saved production
  -> enter Run workspace
  -> start explicit live session
  -> execute current cue
  -> inspect dispatch result
  -> retry or cancel a failed durable command when necessary
  -> use Safe Clear independently when needed
```

Run is intentionally not an editing environment. The operator needs current
and next cue, a prominent GO action, previous/next navigation, Safe Clear,
programme preview, and connection/dispatch state.

```text
+----------------------------------------------------------------+
| LIVE ●  Production name                 API ●  Stream ●        |
+------------------------------+---------------------------------+
| Programme preview            | CURRENT                         |
|                              | Speaker introduction            |
|                              | NEXT: Sponsor takeover          |
+------------------------------+---------------------------------+
| PREVIOUS                      GO                    SAFE CLEAR |
+----------------------------------------------------------------+
```

## Viewer journeys

### Desktop

```text
Open programme
  -> see programme context and live status
  -> watch video as timing centre
  -> see populated surrounding regions
  -> use contextual companion content when present
```

```text
+----------------------------------------------------------------+
| Programme title · Live status · contextual header              |
+-----------+-----------------------------------+----------------+
| Left rail |             Video                 | Right rail     |
|           |       timed broadcast graphics    |                |
+-----------+-----------------------------------+----------------+
| Interactive footer / ticker / choices                           |
+----------------------------------------------------------------+
```

Empty rails collapse, allowing the player to claim the available space rather
than leaving permanent empty boxes.

### Mobile

Mobile is a companion experience, not compressed desktop columns.

```text
+-----------------------------+
| Video                       |
+-----------------------------+
| Programme context           |
+-----------------------------+
| Match | Info | Partners |    |
| Interact                    |
+-----------------------------+
| Touch-friendly panel cards  |
+-----------------------------+
```

### TV

TV remains presentation-first: full-screen video, broadcast-safe overlays,
large typography and only minimal remote-friendly interaction.

## Shared foundations

Implement foundational tokens in the existing applications before broader
screen work. They may share values, but not the same visual personality.

- spacing, typography and responsive breakpoint scale;
- colour/status tokens for live, rehearsal, healthy, pending, failed and
  cancelled states;
- buttons, form fields, cards, panels, badges and confirmation dialogs;
- visible keyboard focus, semantic headings/labels, contrast, reduced motion
  and accessible error announcements;
- Admin: dense, calm, operational; Viewer: content-led, branded, spacious.

## Implementation addendum

### Workspace routing

Prepare, Rehearse and Run must be distinct workspaces with stable, recoverable
URLs rather than conditional sections inside one Admin component.

```text
/admin/productions
/admin/productions/:productionId/prepare
/admin/productions/:productionId/rehearse
/admin/productions/:productionId/run
```

- Refresh restores the workspace and production context from the URL.
- Editing controls never appear in Run.
- Rehearsal state cannot leak into Run.
- Navigating away never silently resets, completes or cancels an execution
  session.

### Shared preview surface

Admin previews must embed or navigate to the real Player application. Admin
must not reimplement presentation graphics or mutate a preview's React state.

```text
/player/:channelId?profile=desktop&rehearsal=1
/player/:channelId?profile=mobile&rehearsal=1
/player/:channelId?profile=tv&rehearsal=1
```

An embedded Player route (for example, an iframe) is acceptable when it uses
the same Player renderer, rehearsal events and profile layout as the audience
experience. It must show clear loading/disconnected states and accurately size
the selected profile.

### Viewer configuration boundary

Viewer-facing context comes from the selected production's persisted
configuration, not hard-coded demonstration copy. The initial bounded fields
are:

```text
programmeTitle
programmeSubtitle
liveLabel
accent
enabledCompanionPanels
companionPanelLabels
viewerContext
```

Absent fields use sensible Viewer defaults. V1.3 deliberately excludes
arbitrary CSS/HTML, uploaded themes and general template authoring.

### Run-entry safety

Entering Run opens a deliberate confirmation surface that states:

- selected production and rundown;
- total and disabled cue counts;
- API and stream status;
- unresolved pending or failed durable commands;
- whether a live execution session already exists.

Starting Run explicitly creates or resumes a live session. A failed durable
revision cannot be hidden at entry. Leaving Run does not change the session;
Complete show, Abandon session and Reset session (where supported) are separate
confirmed operations.

### Run workspace boundary

Run displays only live-operational information: status, connection state,
production/rundown, preview, previous/current/next cue, GO, Safe Clear,
dispatch recovery and session completion. It excludes production metadata,
cue-payload and rundown-order editing.

### Viewer layout rules

Desktop regions collapse from rendered presentation content, not only from
configuration. Empty rails consume no width; header/footer collapse when empty;
one populated rail remains balanced; and reduced-motion users receive no layout
transition animation.

Mobile companion tabs use accessible tab semantics, keyboard navigation and
appropriately sized touch targets. They preserve the selected tab where useful,
hide panels without enabled content unless an explicit empty state exists, and
must never move the video out of view merely by switching panels. Initial
panels remain Match, Info, Partners and Interact.

### Accessibility acceptance

Manual checks cover keyboard-only Admin navigation, focus visibility, semantic
tabs, labelled fields/errors, dialog focus handling, dispatch failure/recovery
announcements, non-colour status indicators, reduced motion, contrast,
heading order, and usable screen-reader names for GO, Safe Clear, Retry and
Cancel.

## Prioritised implementation sequence

1. Add app-level navigation, context and explicit live/rehearsal status.
2. Add the workspace routes, then implement guided Admin empty and error
   states.
3. Split the existing Admin into isolated Prepare, Rehearse and Run workspaces
   without replacing their proven API calls or typed command forms.
4. Add a real-Player preview panel and the bounded production viewer-context
   configuration fields.
5. Add Run-entry confirmation and operational session safeguards.
6. Establish viewer layout tokens and collapse empty desktop rails.
7. Replace mobile compression with tabbed companion panels; preserve TV focus.
8. Apply keyboard, focus, contrast, reduced-motion and screen-reader checks.
9. Run the acceptance story below against the local Compose stack.

## V1.3 acceptance story

```text
New operator opens ShowGather
  -> creates a production through guided Admin
  -> builds a rundown using typed cue editors
  -> previews desktop, mobile and TV output
  -> runs a rehearsal session
  -> enters focused live operation
  -> executes cues and understands dispatch state
  -> recovers from a failed dispatch with retry or cancellation
  -> viewer receives a polished responsive presentation
```

## Completion criteria

- An operator never needs JSON, event IDs or revisions for normal work.
- Prepare, Rehearse and Run are visually and behaviourally distinct.
- Rehearsal cannot be mistaken for live; Safe Clear remains available during
  Run without interrupting video.
- Viewer rails collapse when empty; mobile and TV have intentional layouts.
- New, loading, empty, validation and dispatch-failure states explain a next
  action.
- Keyboard navigation, visible focus, labelled controls, contrast and reduced
  motion have manual acceptance coverage.
- Existing live/rehearsal isolation, immutable sessions, durable snapshots,
  outbox retry/cancel ordering and media-PTS transient scheduling remain
  regression-tested.
