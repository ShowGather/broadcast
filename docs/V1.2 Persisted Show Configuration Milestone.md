# ShowGather V1.2 — Persisted Show Configuration Milestone

## Outcome

ShowGather can now be operated as a saved production system rather than only as
a seeded demonstration:

```text
Create production
  -> copy reusable configuration into that production
  -> build and edit a persisted rundown
  -> save and restart
  -> reopen and execute in live or rehearsal
  -> hydrate a late-joining viewer from durable state
```

The existing presentation timing architecture is unchanged. Canonical commands
continue through the ordered outbox into timed ID3/HLS for live delivery (or
SSE for rehearsal), while Player transient presentation remains governed by
media PTS.

## Delivered

- Persisted production creation, editing and independent duplication.
- Named reusable show configurations per channel and an explicit copy action
  into a production. Later package changes do not rewrite copied production
  configuration.
- Persisted rundown creation, editing and independent duplication.
- Typed score, lower-third, alert, sponsor, ticker and regional-clear cue
  command editing; the Admin does not use raw timed-transport JSON as its
  primary workflow.
- Cue enable/disable, transactional reordering and contiguous positions.
- Explicit live and rehearsal session starts. Each session stores an immutable
  snapshot of cue identity, labels, order, enabled state and canonical command
  data. Edits apply only to later sessions.
- Idempotent seed data that creates only missing records and preserves operator
  modifications.

## Release-candidate evidence

### Clean-clone audit

An isolated clean clone of the committed V1.2 source was tested against a
disposable PostgreSQL 16 database.

- Both committed migrations applied successfully, including
  `20260722155920_persisted_show_configuration`.
- `db:seed` completed repeatedly.
- A deliberate edit to the seeded production title and first cue label survived
  another seed run, demonstrating that seed does not overwrite operator work.

### Manual operator workflow

On the rebuilt local Compose stack, a new acceptance production was created
without relying on the seed, then given a reusable football configuration and a
new rundown.

1. Score, sponsor and disabled-alert cues were added and reordered.
2. A rehearsal session was started, then the sponsor cue was edited. The active
   session retained the original sponsor definition.
3. A later rehearsal session used the edited sponsor definition.
4. The disabled alert was rejected for execution.
5. A rehearsal cue dispatched over the rehearsal path, while a live score cue
   dispatched through the durable live path as revision 7.
6. After API restart, the created production and durable presentation snapshot
   were recovered. The snapshot returned revision 7 and the live score state.

### Automated verification

- API suite: 11 passing tests, including configuration-copy isolation,
  duplication boundaries, contiguous reorder, immutable sessions, disabled-cue
  rejection and prior outbox retry/cancellation regressions.
- Full workspace production build passed for event schema, ID3, presentation
  model, API, Admin and Player.

## Known limitations

- One active API dispatcher process per database is assumed; multi-instance
  production deployment still needs outbox claiming/leases.
- No accounts, permissions, authentication, collaboration, asset uploads,
  template marketplace, analytics, billing or production deployment guarantees.
- Show configurations currently provide a focused football-style typed Admin
  workflow, not a general-purpose graphics/template authoring system.
- The tested environment remains the local Compose/OrbStack pilot stack.
